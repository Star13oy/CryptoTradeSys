# 执行可靠性与消息安全架构说明

> 适用范围：`phase-1` 工作区当前的执行编排、审计、账本和 live 执行边界。
>
> 本文只描述已经能从代码和 README 直接确认的事实，并明确列出还缺失的能力，不把规划写成既成事实。

## 1. 目标

这一阶段的核心目标不是“把所有交易做得更复杂”，而是把执行链路变得可解释、可恢复、可审计。

具体来说，系统要逐步达到下面几件事：

1. 同一笔执行意图不会因为重复提交而重复下单。
2. 消息和状态推进不会乱序到让人无法判断真实执行结果。
3. 任何半完成、失败、恢复中的交易都能被识别、恢复和审计。
4. live 执行必须先过预检，不允许把明显超限或未授权的请求直接送到交易所。
5. 账本、审计、恢复队列之间要能对得上，方便对账和追溯。

这里的“消息不重、不乱、不丢”是目标，不是当前项目已经完全具备的承诺。

## 2. 当前已经做到什么

### 2.1 执行编排已经有了最小闭环

当前的执行核心在 `backend/app/execution/service.py`。它已经能把一笔 `open_hedge / close_hedge` 意图转成一组确定性的状态变化、账本写入和审计事件。

已确认的行为包括：

1. `ExecutionOrchestrator.execute()` 会先检查同一 `trade_id` 是否已经存在可重放的记录。
2. `open_hedge` 和 `close_hedge` 都会把执行结果写入 trade ledger。
3. 每一步关键状态都会产生审计事件。
4. `open_hedge` 在模拟 perp 失败时，会把交易置为 `failed` 并发出 `recovery.required` 事件。
5. live 场景下，如果部分腿成交，会把交易置为 `recovery_pending`，而不是假装已经成功完成。
6. `recover()` 已经支持针对 `failed` 和 `recovery_pending` 状态做人工恢复。

这说明当前项目已经不是“只发请求不管结果”的模式了，而是已经有了执行状态机、账本和审计事件的最小闭环。

### 2.2 已有幂等入口，但还不是完整消息系统

当前已有的幂等处理是在执行入口按 `trade_id` 做的：

1. `open_hedge` 如果发现同一个 `trade_id` 已经处于 `open / hedged / closing / closed / recovery_pending`，会直接返回已有结果。
2. `close_hedge` 如果发现同一个 `trade_id` 已经是 `closed`，也会按幂等重放处理。
3. 重放会记录 `execution.idempotent.replay` 审计事件。

这已经能挡住一部分重复提交，但它只覆盖了“执行入口重复调用”的问题，还没有覆盖消息队列、跨进程重试、乱序投递、重复消费这些更底层的问题。

### 2.3 `recovery_pending` 已经成为真实状态

当前代码里，`recovery_pending` 不是概念占位，而是 live 执行里的真实状态：

1. live 开仓时，如果任一腿返回 `partial`，最终状态会落到 `recovery_pending`。
2. live 平仓时，如果任一腿返回 `partial`，最终状态也会落到 `recovery_pending`。
3. 进入该状态后，会补发 `execution.recovery.required` 审计事件。
4. `ExecutionReadService` 会把 `failed` 和 `recovery_pending` 一起放进恢复队列。

这很重要，因为它把“半成功”从异常日志里拉回到了业务状态里，后续才能做对账、补单和人工处理。

### 2.4 live guard 已经有预检，但范围还有限

当前 live 执行已经有三道前置检查：

1. `live_execution_enabled` 必须开启。
2. symbol 必须在 `live_symbol_allowlist` 里。
3. 请求名义价值不能超过 `max_live_notional`。

这些检查位于执行前置层，能挡住明显不该发出的 live 请求。

不过它现在还是“请求级预检”，还不是完整的 live guard 体系。它没有覆盖运行时熔断、连续失败降级、交易所返回异常后的自动止损，也没有独立守护进程来统一控制 live 风险。

### 2.5 审计和账本已经可查询、可导入

当前的审计和账本不是纯内存结构，而是文件持久化的 JSON 存储：

1. `backend/app/audit/store.py` 会把审计事件保存到配置路径。
2. `backend/app/ledger/store.py` 会把交易账本保存到配置路径。
3. 两者都支持读取、追加和替换。
4. `AuditEventService` 支持按 `severity`、`source` 过滤事件。
5. `TradeLedgerService` 支持按 `mode / status / strategy_id / symbol` 过滤记录。

这意味着当前项目已经具备“可落盘、可回放、可导入”的基础，但还不是数据库级别的强一致持久化。

### 2.6 已经有执行侧的摘要视图

`backend/app/execution/read_service.py` 已经能从账本和审计事件生成一个执行快照，包含：

1. 状态计数。
2. 恢复队列。
3. 最近的严重/警告事件。

这对 console 和人工值守很有价值，因为它把“执行是否健康”从散落的事件里提炼成了可读摘要。

## 3. 当前还缺什么

下面这些是目前还没有从代码里确认到的能力，不能写成已完成。

### 3.1 还没有完整的消息安全基础设施

当前没有看到以下机制：

1. 统一的消息 envelope，例如 `message_id / causation_id / correlation_id / sequence / aggregate_version`。
2. outbox / inbox 模式。
3. 去重表或已消费消息表。
4. 事件顺序校验和乱序重排。
5. 端到端的“至少一次投递 + 幂等消费”闭环。
6. “exactly-once” 语义的真实保证。

因此，当前系统最多只能说“执行入口具备部分幂等”，还不能说已经实现了消息不重不乱不丢。

### 3.2 账本和审计之间没有原子事务

当前账本和审计分别写各自的 JSON 文件，没有看到跨文件的原子提交机制。

这意味着：

1. 执行结果写入账本后，审计写入可能失败，反之亦然。
2. 崩溃恢复后可能出现“账本有了，但审计缺了”或“审计有了，但账本没落好”的情况。
3. 目前没有事务日志来自动修补这种不一致。

所以现在还不能把它当成强一致的执行事实源。

### 3.3 还没有自动恢复 worker 和补偿策略

虽然已经有 `recovery_pending` 和 `recover()`，但还缺：

1. 自动扫描恢复队列并触发恢复动作的 worker。
2. 失败重试策略。
3. 补单与撤单的明确编排。
4. 对真实交易所 fill 状态的持续对账。
5. 失败后 rollback / compensation 的完整闭环。

现在的恢复更像“人工可操作入口”，还不是自动化恢复系统。

### 3.4 还没有 exchange-grade 对账

目前的 ledger 主要记录的是执行侧状态，而不是来自交易所的完整事实流。

缺少的部分包括：

1. 真实订单状态与 ledger 的持续比对。
2. 成交明细、部分成交、撤单、过期、拒单的系统化归档。
3. 用成交回报反推持仓和已实现盈亏的对账链路。
4. 对账差异报告和差异修复流程。

因此，当前的“对账”更多是逻辑上的状态核对，还不是交易所级别的最终对账。

### 3.5 live guard 还缺运行时治理

当前 live guard 只覆盖请求前置条件，还缺：

1. 连续失败熔断。
2. 风险阈值动态下调。
3. 恢复任务和 live 下单之间的调度隔离。
4. 守护进程级别的 live 开关。
5. 对单笔请求之外的总风险限额控制。

也就是说，当前只能算“预检 guard”，不能算“运行时 guard 体系”。

## 4. 推荐的后续演进路线

### 4.1 第一阶段：把消息语义先补齐

优先把“消息不会重、不会乱”的基础打牢。

建议引入：

1. 标准化执行消息 envelope。
2. `message_id` 级别去重。
3. `correlation_id` 贯穿执行、审计、恢复。
4. `aggregate_version` 或顺序号，避免旧消息覆盖新状态。

这一阶段的目标不是把业务做复杂，而是让所有执行、恢复、对账动作都能被唯一标识和排序。

### 4.2 第二阶段：把账本、审计、消息投递从“直接写”改成“可恢复写”

建议补 outbox / inbox 结构：

1. 执行结果先进入本地可恢复写模型。
2. 审计事件先进入 outbox。
3. 下游消费通过 inbox 去重。
4. 任何一步失败都能在恢复流程里继续跑，而不是靠人工猜状态。

这一阶段结束后，系统才更接近真正可恢复的消息处理系统。

### 4.3 第三阶段：把 `recovery_pending` 变成可自动收敛状态

建议新增恢复 worker 和恢复策略：

1. 自动扫描 `recovery_pending` 和 `failed`。
2. 根据事件链路决定是补开、补平、重试还是人工接管。
3. 为每次恢复记录独立审计轨迹。
4. 为恢复动作加幂等键，避免重复恢复。

这一阶段的目标是让半完成交易能自动收口，减少人工介入。

### 4.4 第四阶段：把 live guard 升级为运行时风险控制层

建议把 live guard 从执行前检查扩展为运行时控制层：

1. 对连续失败、异常撤单、部分成交堆积设置熔断条件。
2. 给 recovery worker 和 live executor 做资源和时序隔离。
3. 把全局风险额度、单策略额度和单交易额度统一收口。
4. 为 live guard 保留人工 override，但必须审计。

这样 live 才不是“能发单”，而是“在可控边界内发单”。

### 4.5 第五阶段：把对账变成一等公民

最终要落到交易所事实对账。

建议把以下能力做成正式作业：

1. 拉取交易所订单、成交、持仓事实。
2. 与本地 ledger 做差异比对。
3. 把差异分成可自动修复和需人工处理两类。
4. 对每次差异修复输出审计报告。

这一阶段完成后，系统才真正具备“执行事实可核验”的能力。

## 5. 建议的原则

为了避免后续演进越做越乱，建议始终坚持下面几条：

1. 以 ledger 为业务状态入口，以审计为证据链，以恢复队列为操作入口。
2. 所有恢复动作都必须幂等。
3. 所有 live 动作都必须经过可解释的 guard。
4. 不把“部分成功”隐藏掉，而是显式落到 `recovery_pending`。
5. 不把“重试”当成恢复，重试只是手段，恢复必须能证明最终状态。

## 6. 结论

当前项目已经具备执行编排、账本落盘、审计留痕、幂等重放、`recovery_pending` 识别和基础 live 预检这些关键底座。

但它还没有达到消息系统级别的“不重不乱不丢”，也没有完整的自动恢复、交易所级对账和运行时 live guard 体系。

后续最合理的路线，是先补消息语义和去重，再补可恢复投递和恢复 worker，最后把 live guard 与对账收口做成一等公民。这样才能在不夸大现状的前提下，稳步把执行链路做成可运营、可审计、可恢复的系统。

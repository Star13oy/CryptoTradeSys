# Crypto Funding Arbitrage System Design Spec

**Date:** 2026-04-03
**Topic:** `crypto-funding-arbitrage`
**Status:** Approved direction, implementation in progress

## Goal

设计一个面向个人自营交易者的生产级虚拟币量化交易系统，一期聚焦 `Binance` 单所、`现货-永续对冲`、`资金费率套利`、`24/7 全自动执行`，同时具备高可靠风控、友好前端指挥台、历史数据回测能力，以及支持策略自定义和模型扩展的研究框架。

## Current Implementation Snapshot

截至 `2026-04-05`，项目已经从“设计与原型阶段”进入“后端算法底座 + 多页控制台骨架”阶段。

当前已经落地的关键事实：

1. 前端已具备 7 个 Stitch 对齐页面的原型级实现，而不是只剩首页和扫描页。
2. 后端已具备真实 Binance 公共行情读取、控制台只读 API 和 typed contract。
3. 评分引擎已从简单单期净收益模型演进到带 `projected edge / payback / expected hold periods` 的持有周期视角。
4. 后端已落地 `strategy registry + risk policy + backtest engine + algo API`。
5. 已批准并开始实现“离线复盘学习中心”：基于已完成交易样本产出一键建议包，且样本已经有后端持久化入口，但任何参数改动都必须经过人工确认。
6. 已补充交易账本提取器，可把 completed trade journal records 稳定地转换为学习样本，并支持按 symbol 和最近 N 条过滤。
7. 已补充第一版历史回测数据集仓库，支持导入、列出、按数据集回放，以及用历史数据集对 tuning package 做预验证。
8. 已补充第一版 execution orchestrator，能把 `open_hedge / close_hedge` 意图转成确定性的 ledger 状态迁移与审计事件流，为后续 live adapter 铺底。

这意味着设计文档中的大量模块已不再只是目标，而是需要继续向“真实执行闭环”和“历史数据驱动优化”延展。

## Confirmed Scope

本设计基于当前已确认的边界：

1. 单独立项，不复用现有 `FundSelection` 仓库。
2. 一期交易所为 `Binance` 单所。
3. 一期核心策略为 `现货-永续对冲` 下的 `资金费率套利`。
4. 系统支持 `Paper Trading` 与 `Live Trading` 双模式。
5. 运行方式为 `24/7 全自动`，支持自动开仓、自动维持、自动再平衡、自动平仓。
6. 用户画像为 `个人自营`，非团队资管平台。
7. 市场扫描可覆盖全市场，但实盘执行必须经过可配置白名单准入。
8. 成功标准采用 `安全、收益、效率` 三者均衡的路线，而不是单点极致。
9. 必须支持历史数据回测，以及可插拔的策略/模型自定义框架。
10. 前端以 `交易指挥台` 为核心，而不是研究报告型界面。
11. 系统允许基于历史交易结果做离线自我总结和参数建议，但不允许未经人工确认直接修改实盘运行参数。

## Non-Goals

一期明确不做：

1. 多交易所联动套利。
2. DEX 与链上执行。
3. 面向外部客户的多租户资管平台。
4. 高频做市、超低延迟撮合、微秒级执行优化。
5. 把统计套利、机器学习择时、多策略投资组合当作首要交付。
6. 不做未经确认的在线自修改实盘策略，不做“模型自动学习后直接上线交易”。

## Product Positioning

这不是一个“只会算信号”的研究工具，也不是一个“只会下单”的脚本集合，而是一个完整的交易闭环系统：

1. 它要能持续扫描资金费率套利机会。
2. 它要能用交易成本、仓位风险和保证金占用去过滤伪机会。
3. 它要能安全地执行现货与永续双腿。
4. 它要能在异常、断流、滑点、单腿成交失败时保护账户。
5. 它要能把所有关键行为以图形化方式展示给操作者。
6. 它要能为未来的新策略、新模型、新交易所保留扩展位。

## Design Decision

推荐采用 `模块化单体 + 事件驱动内核 + 双模式运行（Paper / Live）`。

这个方案适合当前阶段，原因如下：

1. 单机部署、个人自营、单所起步，不需要过早承担微服务复杂度。
2. 策略、执行、风控、回测、前端 API 可以清晰分层，避免后续重构过大。
3. 事件驱动适合处理行情流、账户流、订单流、告警流与回测回放。
4. 后续若扩展到多交易所、多账户、多策略，模块边界已提前打好。

## System Architecture

### 1. Exchange Gateway

职责：

1. 接入 Binance REST / WebSocket。
2. 获取现货、永续、资金费率、账户、持仓、订单与合约元数据。
3. 处理签名、限流、重试、时间同步与幂等。

设计要求：

1. 策略层不能直接依赖 Binance SDK 细节。
2. 外部请求必须有超时、重试、熔断与降级策略。
3. 行情、账户、订单、资金费率应拆成独立同步通道。

### 2. Market Data Service

职责：

1. 清洗原始行情并组装标准市场快照。
2. 统一输出现货盘口、永续盘口、标记价格、指数价格、资金费率与交易成本估算。
3. 对交易对打上流动性、可交易性、白名单、风险冻结等状态标签。

设计要求：

1. 策略看到的是“可决策对象”，不是原始 API 报文。
2. 快照应包含时间戳、来源、延迟、完整性状态。
3. 要保留回放能力，供回测与问题复盘使用。

### 3. Opportunity Engine

职责：

1. 从全市场快照里筛选候选标的。
2. 计算资金费率套利机会评分。
3. 输出推荐等级、建议仓位、预计持有窗口和风险标签。

一期核心评分维度建议：

1. 预期资金费率净收益。
2. 手续费与滑点侵蚀。
3. 盘口深度与成交稳定性。
4. 保证金占用效率。
5. 现货与永续的净敞口偏离风险。
6. 历史资金费率稳定性与可重复性。
7. 标的波动水平与异常事件风险。

### 4. Strategy Runtime

职责：

1. 承载运行中的策略实例。
2. 管理策略参数、模型版本、模式切换、暂停恢复。
3. 将机会评分转化为标准化的交易意图。

标准输入：

1. 市场快照。
2. 账户状态。
3. 风控预算。
4. 白名单配置。
5. 策略参数与模型版本。

标准输出：

1. `NO_ACTION`
2. `OPEN_CANDIDATE`
3. `REBALANCE_CANDIDATE`
4. `REDUCE_CANDIDATE`
5. `CLOSE_CANDIDATE`
6. `FORCE_RISK_EXIT`

### 5. Execution Orchestrator

职责：

1. 把策略意图转成实际订单序列。
2. 计算开仓顺序、拆单策略、价格保护与超时处理。
3. 管理部分成交、补对冲、失败回滚和执行结果回写。

设计要求：

1. 不追求盲目最快成交，而是优先控制裸方向暴露。
2. 任一腿失败时必须进入补救状态机。
3. 每次执行都要生成可审计事件流。

### 6. Risk Guard

职责：

1. 以高于策略层的优先级管理风控。
2. 决定是否允许开仓、加仓、减仓或只读运行。
3. 触发告警、熔断、降级与风险退出。

关键风控对象：

1. 账户总风险预算。
2. 单标的风险预算。
3. 保证金率阈值。
4. 对冲偏离阈值。
5. 连接状态与数据新鲜度。
6. 连续异常订单与接口失败。
7. 黑名单、冷静期与人工冻结。

### 7. Portfolio Hedge Manager

职责：

1. 跟踪现货与永续持仓配比。
2. 管理自动再平衡、补对冲与减仓。
3. 统一视图展示净敞口、名义敞口、保证金占用与未实现盈亏。

### 8. Data and Research Platform

职责：

1. 存储行情、资金费率、特征、订单、成交、持仓、账户权益与告警日志。
2. 支持历史回测、情景回放、参数扫描与策略版本对比。
3. 为自定义模型框架提供数据与运行入口。

补充要求：

1. 研究平台除了传统回测外，还要支持“事后复盘学习”，即把已完成交易和当时的评分/风险上下文重新聚合，形成调参建议。
2. 这类建议应优先追求稳定性，而不是盲目追求收益最大化。
3. 学习输出不直接改写实盘配置，而是生成可审阅、可确认的一键建议包。
4. 建议包在进入人工确认前，应优先允许在历史数据集上做一次快速 replay，对比 `保守 / 平衡 / 进取 / 自动推荐` 的历史窗口表现。

### 9. Console API and Frontend

职责：

1. 提供交易指挥台、回测工作台、策略配置、风控配置与审计接口。
2. 作为前端与核心交易模块之间的唯一应用边界。
3. 屏蔽内部实现细节，只暴露稳定业务模型。

## Core Trading Lifecycle

### 1. 市场扫描

系统持续拉取：

1. 现货盘口与成交。
2. 永续盘口、标记价格、指数价格。
3. 当前与预测资金费率。
4. 账户余额、持仓、杠杆与保证金信息。
5. 交易规则、精度、最小下单量与状态标志。

### 2. 候选机会预筛

预筛建议剔除：

1. 不在交易白名单内的标的。
2. 流动性不足或盘口深度不达标的标的。
3. 手续费后预期净收益过低的标的。
4. 合约状态异常或 API 数据不完整的标的。
5. 被风控冻结、处于冷静期或黑名单中的标的。

### 3. 机会评分

建议输出以下结果：

1. 机会总分。
2. 预计净收益区间。
3. 资金占用效率。
4. 预计持有时长。
5. 风险标签。
6. 建议仓位上限。

### 4. 开仓前审批

必须经过独立风控校验：

1. 是否超过账户总风险预算。
2. 是否超过单标的仓位上限。
3. 当前保证金率是否足够健康。
4. 与现有持仓叠加后是否形成过度集中。
5. 当前系统是否处于降级或熔断模式。

### 5. 开仓执行

执行层需要管理：

1. 现货腿与永续腿的数量换算。
2. 下单顺序和价格保护。
3. 订单拆分、滑点控制与超时撤单。
4. 一腿成交一腿失败时的补对冲。
5. 执行结果的最终一致性落账。

### 6. 持仓维持

开仓后持续检查：

1. 对冲比例偏离。
2. 保证金率变化。
3. 资金费率预期是否转弱或反转。
4. 标记价异常偏离。
5. 持仓是否超过最大持有时长。

### 7. 平仓与风险退出

触发条件建议包括：

1. funding 优势消失。
2. 预期净收益不能覆盖交易成本。
3. 风控要求减仓或清仓。
4. 系统进入高危异常状态。
5. 达到止盈、止损、超时退出条件。

### 8. 复盘归档

每次机会与交易都必须落地：

1. 触发时间与快照版本。
2. 评分结果与参数版本。
3. 风控判断。
4. 订单明细与成交明细。
5. 开平仓后账户状态。
6. 收益分解与异常标签。

## Risk Control Framework

### 1. 事前风控

1. 白名单准入。
2. 黑名单冻结。
3. 单标的最大名义仓位。
4. 单账户最大总敞口。
5. 最低预期净收益门槛。
6. 最低盘口深度门槛。
7. 最低数据完整性要求。

### 2. 事中风控

1. 保证金率三级阈值：预警、限制开仓、强制风险退出。
2. 对冲偏离阈值：超阈值后先补对冲，再限制加仓。
3. 单腿成交超时保护。
4. 行情断流保护：禁止新开仓，仅保留减仓能力。
5. API 错误与限流熔断。
6. 连续异常订单熔断。
7. 极端波动熔断。

### 3. 事后风控

1. 每日收益与回撤归因。
2. 异常订单复盘。
3. 风控动作审计。
4. 参数变更与模式切换记录。
5. 实盘与回测偏差分析。

### 4. 风控优先级原则

1. 风控优先级高于策略。
2. 风控可以拒绝策略开仓。
3. 风控可以要求策略减仓。
4. 风控可以把系统降级为只读或仅减仓模式。

## Failure Handling and Recovery

系统必须把异常视为常态流程，而不是边角逻辑。

关键异常场景：

1. 行情断流。
2. 账户同步失败。
3. 一腿成交一腿失败。
4. 资金费率突变。
5. 保证金快速恶化。
6. 交易所接口限流或签名失败。
7. 进程崩溃后的状态恢复。
8. 高风险配置变更。

恢复原则：

1. 先恢复状态，再恢复决策。
2. 无法确认账户状态时，不允许新开仓。
3. 恢复期间优先确保风险可见、仓位可控。
4. 所有自动恢复动作都必须带审计记录。

## Historical Backtesting and Replay

### 1. 回测目标

系统不仅要支持“历史收益回放”，还要支持接近实盘约束的事件回测。

必须覆盖：

1. 历史资金费率回测。
2. 历史行情与盘口快照回放。
3. 手续费、滑点、冲击成本建模。
4. 风控阈值对策略表现的影响。
5. 不同参数版本之间的横向比较。

### 2. 回测模式

建议支持三类模式：

1. `Fast Backtest`
基于 K 线、资金费率与简化成交模型做参数筛选。

2. `Event Replay`
基于标准化事件流回放，更接近实盘状态机。

3. `Shadow Simulation`
对接实时行情但不下真实单，用于实盘前影子运行。

### 3. 回测输出

1. 总收益、年化、夏普、最大回撤。
2. 单笔机会胜率与收益分布。
3. 资金利用率。
4. 持仓时长分布。
5. 真实成本侵蚀分析。
6. 熔断触发次数与风控影响。
7. 参数对结果敏感性分析。

### 4. 离线复盘学习

在回测与回放之外，一期后续还要支持一条“离线自我总结”链路：

1. 输入：
   - 已完成交易结果
   - 开仓时评分明细
   - 风控标签
   - 实际持有时长、实际收益、最大回撤
   - 从交易账本中确定性提取出来的学习样本
2. 输出：
   - `保守 / 平衡 / 进取 / 系统自动推荐` 四类建议包
   - 每个建议包附带可解释的文字摘要和风险理由
   - 所有参数改动都必须以“人工确认后应用”为终点
3. 设计原则：
   - 自动推荐默认采用 `稳定优先`
   - 不向用户暴露一堆难懂的底层参数名，而是以“建议包”形式交付
   - 允许高级用户查看参数 diff，但不把这作为主交互路径
   - 学习样本不仅可以手工导入，也可以从 completed trade journal records 中按 symbol / recent-N 进行稳定提取后复用

## Custom Strategy and Model Framework

### 1. 设计目标

自定义模型框架的目标不是一期就做“重机器学习平台”，而是先把扩展接口设计正确，让你后面能安全地加新因子、新评分器和新策略。

### 2. 建议的扩展边界

1. `Feature Builder`
负责从行情、资金费率、账户状态生成标准特征。

2. `Signal / Scoring Model`
负责把特征转成机会评分或仓位建议。

3. `Policy Layer`
负责业务规则、白名单、黑名单、风险偏好与模式切换。

4. `Execution Policy`
负责把目标仓位转成下单细节。

### 2.5 一键建议包与人工确认

为了让不懂算法的使用者也能安全使用系统，模型框架需要再补一层产品化包装：

1. 系统内部仍然维护细粒度参数，例如评分权重、basis 惩罚、slow-payback 门槛等。
2. 面向用户展示时，不直接暴露底层参数，而是生成：
   - `保守方案`
   - `平衡方案`
   - `进取方案`
   - `系统自动推荐`
3. 用户操作模型优化时，主交互是“一键应用建议包”，而不是手动编辑几十个参数。
4. 即便是一键应用，也必须经过明确确认，不允许后台自动生效。

### 3. 模型接口要求

每个模型都应有统一接口：

1. 输入特征 schema。
2. 输出结果 schema。
3. 版本号。
4. 参数定义。
5. 可解释字段。
6. 回测兼容性约束。

### 4. 一期建议支持的模型类型

1. 规则加权评分器。
2. 参数化资金费率打分器。
3. 预留机器学习排序器接口。
4. 预留波动过滤器与风险预测器接口。

### 5. 模型治理要求

1. 任一模型版本都要可回放。
2. 任一回测结果都要绑定具体参数与代码版本。
3. Live 模式只允许启用已登记、已校验的模型版本。
4. 模型上线前必须先经过 Paper 或 Shadow 运行。

## Frontend Information Architecture

前端主轴应是 `交易指挥台`，目标是让操作者在 10-20 秒内理解系统是否健康、是否有可开仓机会、当前风险是否可控。

### 页面 1：总览指挥台

核心模块：

1. 顶部全局状态栏
显示运行模式、交易所连接状态、策略状态、是否允许新开仓、最近一次风险动作。

2. 账户健康面板
显示总权益、可用余额、保证金率、净敞口、当日 PnL、累计 PnL、资金利用率。

3. 机会扫描面板
显示当前 Top opportunities、预计净收益、资金费率、建议仓位、白名单状态、风险标签。

4. 持仓与对冲面板
显示现货腿、永续腿、对冲偏离、持仓时长、下一次 funding 窗口。

5. 风控告警面板
显示预警、限制开仓、熔断、异常恢复等事件。

6. 系统运行面板
显示数据延迟、心跳、任务队列、最近失败任务和恢复动作。

### 页面 2：机会扫描页

1. 全市场扫描结果表格。
2. 白名单过滤器。
3. 收益/成本/风险多维排序。
4. 单标的详情抽屉。
5. 手续费、滑点、资金利用率解释。

### 页面 3：持仓监控页

1. 当前持仓卡片。
2. 对冲偏离趋势图。
3. 资金费率收益分解。
4. 开仓原因与平仓条件。
5. 一键切换到只减仓模式的人工干预入口。

### 页面 4：风控中心

1. 风险阈值设置。
2. 当前熔断状态。
3. 异常事件时间线。
4. 黑白名单配置。
5. 人工冻结/解冻控制。

### 页面 5：回测实验室

1. 策略选择器。
2. 参数配置器。
3. 时间范围选择。
4. 回测结果总览。
5. 资金曲线、回撤曲线、收益分布与交易明细。
6. 多版本结果对比。

### 页面 6：模型工作台

1. 特征列表。
2. 模型版本列表。
3. 参数模板。
4. 可解释输出预览。
5. 上线前校验状态。

### 页面 7：审计与日志中心

1. 配置变更记录。
2. 模式切换记录。
3. 风控动作日志。
4. 订单生命周期时间线。
5. 异常恢复记录。

## UX Principles

### 1. 交互目标

1. 让用户先看懂状态，再做操作。
2. 对高风险操作提供明显确认与解释。
3. 在复杂数据面前保持层级清晰，不堆砌图表。

### 2. 视觉方向

1. 专业、冷静、可信。
2. 主色建议用深海军蓝、石墨灰、青绿色点缀，不用泛紫科技风。
3. 风险颜色分级明确，但不制造恐慌式界面。
4. 重点模块用大卡片和高对比数字，而不是密集文本。

### 3. 关键交互原则

1. 所有关键状态要支持 glanceable view。
2. 详情信息尽量通过抽屉和分层展开，不压垮首页。
3. 风险告警要说明“发生了什么、影响什么、系统做了什么、你能做什么”。
4. 实盘与仿真必须在视觉上强区分，避免误操作。

### Backend

1. `Python 3.11+`
2. `FastAPI`
3. `SQLAlchemy`
4. `PostgreSQL` 作为主业务数据库
5. `Redis` 作为缓存、事件协调与短期状态存储
6. `Pydantic` 统一 schema
7. Binance API 适配层与自建统一网关封装

### Quant / Data

1. `pandas`
2. `numpy`
3. `polars` 可作为高性能研究层增强选项
4. 批任务与回测任务可采用独立 worker

### Frontend

1. `React`
2. `TypeScript`
3. `Vite`
4. `TanStack Query`
5. `Zustand` 或同类轻量状态方案
6. `ECharts` 或同级图表库
7. 统一设计 token 与组件库

### Deployment

1. 一期按单机部署设计。
2. 进程拆分建议为 API、market worker、strategy worker、execution worker、scheduler。
3. 使用 `Docker Compose` 管理本地与单机生产环境。

## Security and Compliance Boundaries

1. API Key 必须最小权限化。
2. 私钥与敏感配置不能明文散落在代码库。
3. 所有高风险配置改动必须记录操作者、时间与变更内容。
4. 前端必须显著展示“系统输出不构成投资建议，实盘风险自担”。
5. Live 模式的切换要有二次确认和视觉警示。

## SLO and Non-Functional Requirements

### 1. 可用性

1. 系统应支持 24/7 长时间运行。
2. 任一关键进程失效后，应有自动恢复与明确告警。

### 2. 可靠性

1. 无法确认账户状态时禁止新开仓。
2. 对冲偏离不能长时间无感存在。
3. 风控模块必须具备优雅降级与熔断能力。

### 3. 性能

1. 机会扫描结果应在秒级刷新。
2. 指挥台关键指标应在可接受的低延迟范围内展示最新状态。
3. 回测支持批量参数实验，但不要求一期做到分布式并行集群。

### 4. 可追踪性

1. 所有订单、告警、熔断、参数变更都必须可检索。
2. 任一交易结果都要能追溯到数据、参数、模型与执行记录。

## MVP Milestones

### M1：交易闭环打通

1. Binance 单所接入。
2. 资金费率套利机会扫描。
3. 白名单配置。
4. Paper Trading 下的自动开平仓。
5. 基础交易指挥台。

### M2：风控与持仓维持

1. 风控中心。
2. 自动再平衡与补对冲。
3. 熔断与降级机制。
4. 告警与审计日志。
5. Live 模式受控上线。

### M3：研究与策略扩展

1. 历史回测引擎。
2. 参数实验与结果对比。
3. 模型工作台。
4. 可插拔评分器与模型版本管理。
5. 离线复盘学习中心与一键建议包。

## Current Gap To MVP

虽然方向已经明确，但截至 `2026-04-05` 仍存在这些核心差距：

1. 还没有 authenticated execution、订单状态机和持仓账本。
2. 还没有真正的历史市场数据仓库，当前回测引擎仍以 deterministic replay 内核为主。
3. 还没有把离线建议包完整接到前端 `模型工作台 / 回测实验室`。
4. 还没有真正的 live risk daemon、rebalance loop 和 recovery worker。

## MVP Acceptance Criteria

1. 系统可在 Paper 模式完成“扫描 -> 评分 -> 开仓 -> 维持 -> 平仓 -> 复盘”闭环。
2. 系统可在 Live 模式对经过白名单准入的标的执行自动套利。
3. 任一自动开仓都必须经过独立风控审批。
4. 一腿成交失败时，系统必须进入可观察、可恢复的补对冲流程。
5. 前端指挥台可清晰展示账户健康、机会列表、持仓、风控状态和异常事件。
6. 系统支持历史回测，并能对不同参数/模型版本输出可比较结果。
7. 策略模型具备统一接口，后续可扩展而无需重写交易内核。

## Summary

这套设计把一期目标收敛得很明确：

1. 用最小可行的交易所与策略边界，尽快打通安全的实盘闭环。
2. 用模块化单体控制复杂度，但提前为多策略、多模型、多交易所扩展打好接口。
3. 用交易指挥台强化可视化与可控性，而不是把系统做成难以理解的黑箱。
4. 从第一天开始把风控、审计、回测和模型治理纳入核心范围，而不是后补。
